<h1>alibi</h1>

<p><strong>У каждого зелёного теста должно быть алиби.</strong></p>

Агент говорит, что баг починен и тесты проходят. `alibi` возвращает исходный код
в состояние до правки, прогоняет тесты, которые агент только что написал, и
показывает те, что всё равно проходят. Тест, который никогда не был красным,
ничего не проверил.

Никакая модель ни о чём не спрашивается. Ни ключа API, ни сети, ни телеметрии.
Вопрос задаётся git и вашему тестовому раннеру, и ответ каждый раз один и тот же.

## Установка

Для кодового агента — он запускает проверку сам, прежде чем сказать «готово»:

```
npx skills add BOTIROFF-D/alibi
```

Работает с Claude Code, Cursor, Codex CLI, Copilot CLI, Gemini CLI, Windsurf,
Cline, OpenCode, Zed и всем, что читает `SKILL.md` или `AGENTS.md`.

Для вас и для CI:

```
npm install -g @botiroff/alibi
alibi
```

Node 18.17 и новее. Ноль зависимостей в рантайме.

## Зачем это нужно

Цифры не мои, и они сходятся друг с другом:

- **75.8%** проваленных прогонов кодовых агентов в AppWorld всё равно сообщили об
  успехе; в однопользовательских доменах tau2-bench — 45–48%.
  ([From Confident Closing to Silent Failure](https://arxiv.org/abs/2606.09863), Advani, июнь 2026)
- Спросить другую модель — примерно то же, что подбросить монету: **ни одна
  конфигурация из 5 судей и 5 стратегий промпта не превысила AUROC 0.65**, а на
  AppWorld те же судьи дали 0.54. Судья читает уверенную интонацию финального
  абзаца, а не состояние машины. (та же работа)
- Из 4 882 пул-реквестов, сделанных агентами, те, что меняли и код, и тесты,
  улучшили покрытие относительно существующего набора в **35.9%** случаев на Java
  и в **22.5%** на Python.
  ([Test Coverage Analysis of Agentic Pull Requests](https://arxiv.org/abs/2607.18057), июль 2026)
- Самая частая жалоба на ИИ в опросе Stack Overflow 2025 года (49 000+
  разработчиков) — **«почти правильно, но не совсем» (45%)**; **66%** сказали,
  что тратят больше времени на починку этого «почти правильного».

Общее у всех этих чисел одно: единственным, кого спросили, сделана ли работа,
был тот, кто её делал.

## Что проверяется

**1. Диф, до всякого запуска.** Удалённый тест, тест, у которого появился
`skip`, тест, тихо потерявший половину ассертов. Это читается прямо из
`git diff` и сообщается как факт, потому что это и есть факт.

**2. Прогон на алиби.** Во временном git-worktree создаётся состояние на базовой
ревизии — мир до правки. Поверх него кладутся новые и изменённые *тестовые*
файлы. Исходный код остаётся старым. Затем каждый новый или изменённый тест
запускается отдельно, и читается только код возврата.

- Тест падает → у него есть **алиби**. Он является доказательством правки.
- Тест проходит → алиби **нет**. Возможно, он проверяет что-то настоящее, но не
  эту правку.
- Тест вообще не запустился, потому что импортирует код, которого ещё не
  существовало → **provisional**. Для нового модуля это ожидаемо и не
  доказывает ничего ни в одну сторону.

**3. Статическое чтение новых тестов.** Ассерты, которые не могут упасть,
тесты вообще без ассертов, одинокий `toBeDefined`, снапшот, записанный тем же
прогоном, который его читает, замоканный субъект проверки. Это совпадения по
шаблону, поэтому они сообщаются как *unproven* и никогда как ложь.

**4. Мутации изменённых строк** (`--mutate`, по умолчанию выключено). Каждая
строка, которую тронула правка, портится по одной — сравнение ослабляется,
конъюнкция превращается в дизъюнкцию, охранное условие убирается, — и тестам
даётся шанс возразить. Выживший мутант — строка, за которой никто не смотрит.

**5. Реестр утверждений.** `.alibi/claims.md` содержит то, что утверждает автор
правки, по строке на утверждение, с тегом вида доказательства, которое его
решает. Английский текст здесь не читается: тег выбирает проверку, предложение
после него — для человека.

```markdown
- [tests] покрывает путь повторной попытки
- [fix] починена гонка в SessionStore.flush
- [pass] набор тестов проходит
- [safe] ни один тест не удалён, не выключен и не ослаблен
```

Утверждения с тегом `perf` всегда возвращаются как unproven с просьбой
приложить бенчмарк. Отказ оценивать то, что невозможно измерить, — и есть смысл
этого файла.

## Коды возврата

| Код | Значение |
| --- | --- |
| `0` | ничего ложного |
| `1` | зелёная ложь или утверждение, которому противоречат факты |
| `2` | что-то просто не доказано, и передан `--strict` |
| `3` | инструмент не смог ответить — нет раннера, нет репозитория, плохие опции |

## Ограничения

- **Корректность правки не доказывается.** Находятся только тесты, которые ей не
  являются доказательством. Пустой отчёт значит, что ничего не поймано, а не то,
  что всё в порядке.
- **Про тесты, которых не касался диф, не говорится ничего.** Какое у них было
  алиби, такое и осталось.
- **Юнит-тесты в Rust лежат в том же файле, что и код.** Откат исходника откатил
  бы и тест, поэтому блоки `#[cfg(test)]` внутри изменённого файла не трогаются и
  помечаются как непроверенные, а не угадываются.
- **Во временном worktree ничего не устанавливается.** Директории зависимостей
  линкуются, а не собираются.
- **У статического чтения бывают ложные срабатывания** — именно поэтому оно
  никогда не порождает ложь.
- **Тесты запускаются по одному процессу на тест.** На наборе с тяжёлой общей
  подготовкой это медленно. Быстрого режима, доверяющего разбору вывода, нет:
  разбор вывода — ровно то, чему этот инструмент отказывается доверять.
