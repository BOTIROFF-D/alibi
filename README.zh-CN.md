<h1>alibi</h1>

<p><strong>每一个通过的测试都需要一个不在场证明。</strong></p>

智能体说 bug 修好了、测试全绿。`alibi` 会把源码恢复到改动之前的状态，重新运行它刚
写的那些测试，然后告诉你哪些测试依然通过。一个从未红过的测试，并没有验证这次改动。

不向任何模型提问。不需要 API key，不联网，不采集数据。它只问 git 和你自己的测试
运行器，而且每次给出的答案都一样。

## 安装

给编码智能体用 —— 让它在说“完成”之前自己先跑一遍：

```
npx skills add BOTIROFF-D/alibi
```

支持 Claude Code、Cursor、Codex CLI、Copilot CLI、Gemini CLI、Windsurf、Cline、
OpenCode、Zed，以及任何会读取 `SKILL.md` 或 `AGENTS.md` 的工具。

给你自己和 CI 用：

```
npm install -g @botiroff/alibi
alibi
```

需要 Node 18.17 及以上。运行时零依赖。

## 它为什么存在

下面的数字不是我测的，而且它们互相印证：

- 在 AppWorld 中失败的编码智能体轨迹里，仍有 **75.8%** 报告成功；在
  tau2-bench 的单控制域中为 45–48%。
  ([From Confident Closing to Silent Failure](https://arxiv.org/abs/2606.09863)，Advani，2026 年 6 月)
- 让另一个模型来判断，几乎等同于抛硬币：**5 个裁判模型 × 5 种提示策略，没有任何
  一种配置的 AUROC 超过 0.65**，在 AppWorld 上同样的裁判只有 0.54。裁判读到的是
  收尾语气里的自信，而不是机器的实际状态。（同一篇论文）
- 在 4,882 个由智能体生成的 PR 中，同时改动代码与测试的那些，相比原有测试真正
  提升了覆盖率的只占 Java 的 **35.9%**、Python 的 **22.5%**。
  ([Test Coverage Analysis of Agentic Pull Requests](https://arxiv.org/abs/2607.18057)，2026 年 7 月)
- 2025 年 Stack Overflow 面向 49,000+ 开发者的调查中，关于 AI 最普遍的抱怨是
  **“几乎对了，但差一点”（45%）**，并且 **66%** 的人表示要花更多时间去修这些
  “几乎对了”的代码。

这些数字共同指向同一件事：唯一被问到“活干完了没有”的，正是干这件活的那一个。

## 它检查什么

**1. 先读 diff，什么都还没运行。** 被删掉的测试、新加了 `skip` 的测试、悄悄少了
一半断言的测试。这些直接从 `git diff` 读出，并作为事实报告——因为它们本来就是事实。

**2. 不在场证明的运行。** 在临时 git worktree 中检出基线版本——也就是改动之前的
世界，再把新增和修改过的**测试文件**覆盖上去，源码保持旧的。然后逐个运行每一个
新增或修改的测试，只读取退出码。

- 测试失败 → 它有 **alibi**，它是这次改动的证据。
- 测试通过 → 它 **没有** alibi。它也许测了某些真实的东西，但不是这次改动。
- 测试根本没跑起来，因为它导入的代码当时还不存在 → **provisional**。对新模块来说
  这是意料之中的，任何一个方向都不构成证据。

**3. 对新测试做静态阅读。** 不可能失败的断言、完全没有断言的测试、孤零零的
`toBeDefined`、由同一次运行写入又读取的快照、把被测对象直接 mock 掉的测试。这些
都是模式匹配，因此只报告为 *unproven*，永远不会升级为“谎言”。

**4. 对改动行做变异**（`--mutate`，默认关闭）。改动触及的每一行被逐一破坏——放松
比较、削弱合取、去掉守卫条件——然后给测试一个提出异议的机会。存活下来的变异体，
说明那一行没有任何测试在盯着。

**5. 声明账本。** `.alibi/claims.md` 记录改动作者声称的内容，一行一条，并标注哪
一类证据能够裁决它。这里不解析自然语言：标签决定用哪项检查，后面的句子是给人看的。

```markdown
- [tests] 覆盖了重试路径
- [fix] 修复了 SessionStore.flush 中的竞态
- [pass] 整个测试套件通过
- [safe] 没有删除、跳过或削弱任何已有测试
```

`perf` 类声明永远返回 unproven，并提示附上基准测试。拒绝评判自己无法测量的东西，
正是这个文件存在的意义。

## 退出码

| 退出码 | 含义 |
| --- | --- |
| `0` | 没有虚假之处 |
| `1` | 存在“绿色谎言”，或某条声明与证据矛盾 |
| `2` | 仅仅是未被证明，且传入了 `--strict` |
| `3` | 工具无法作答——没有运行器、不是仓库、参数有误 |

## 局限

- **它无法证明改动是正确的。** 它只能找出那些并不构成证据的测试。报告为空意味着
  什么都没抓到，而不是什么都没问题。
- **对 diff 没有触及的测试，它什么也不说。**
- **Rust 的单元测试与源码同处一个文件。** 回退源码会把测试一起回退，因此改动文件
  内的 `#[cfg(test)]` 块不做处理，并标记为未检查，而不是猜测。
- **临时 worktree 不安装任何东西。** 依赖目录是链接过去的，不会重新构建。
- **静态阅读会有误报**，这正是它永远不能产生“谎言”的原因。
- **每个测试各起一个进程。** 对于全局初始化很重的套件会比较慢。没有“信任解析输出”
  的快速模式：解析输出正是这个工具拒绝信任的东西。
